# HUMANユーザーテストガイド

この文書は、CLI CommentatorをHUMANが実際に使い、設定の分かりやすさ、操作感、表示、音声、安心感を評価するための説明書兼チェックシートです。

## 最重要方針

- このテストは公開可否を決めるものではありません。
- チェック項目がすべて通っても、自動的に「公開してよい」とは判断しません。
- HUMAN自身が日常的な使い方を試し、体感を含めて十分に納得するまで公開しません。
- 使いにくさ、迷い、不安、疲れ、表示の違和感があれば、動作上のエラーでなくても改善対象です。
- 違和感があれば記録し、修正し、必要な範囲から再テストします。回数や期限は固定しません。
- タグ作成、Release公開、配布、Updater提供は、この文書の作業範囲外です。必ず別途HUMANが判断します。

現在の最初の対象は、PTYサイズ同期修正を含む **v0.2.2 Unsigned候補**です。v0.2.1はManaged Terminalの表示不良が確認されているため、公開No-Goのまま扱います。

## 1. テストで見るもの

自動テストではなく、次のHUMAN体験を確認します。

1. 初めて画面を見ても、どこから始めるか分かるか
2. Claude Codeを起動し、普段の作業を安全に続けられるか
3. 文字、罫線、カーソル、スクロールが自然に見えるか
4. ウィンドウサイズを変えても画面が崩れないか
5. 実況と解説が役に立ち、邪魔にならないか
6. 読み上げが聞き取りやすく、うるさすぎないか
7. エラーや切断が起きたとき、次に何をすればよいか分かるか
8. 15〜30分以上使っても、遅さ、疲れ、苛立ちを感じないか
9. 承認画面や重要な出力を、誤読せず安心して判断できるか

## 2. 役割

### HUMAN

- 実際にアプリを操作する
- 良い点、悪い点、迷った点を体感の言葉で記録する
- 修正後に再テストする
- 公開するかどうかを、テストとは別に最終判断する

### Codex / AIエージェント

- テスト用ビルドの準備、導入、復元を支援する
- バージョン、commit、ログ、スクリーンショットを整理する
- 不具合を再現し、Issue、Todoist、修正PRへつなげる
- HUMANの許可なしに公開、配布、マージを行わない

## 3. テスト前の準備

### 3.1 記録する情報

開始前に次をメモします。

```md
- テスト日時:
- テスター:
- アプリバージョン:
- commit:
- 入手元またはビルド元:
- Mac: Apple Silicon / Intel
- macOSバージョン:
- Claude Codeバージョン:
- 主に使う作業フォルダ:
- 画面サイズ・外部ディスプレイ:
- TTS: オン / オフ
```

アプリのバージョンと環境は、`Desktop Server`パネルの`Version`と`Platform`で確認できます。問題報告時は`Copy Version/Platform`または`Copy Debug bundle`を使います。

### 3.2 安全確認

- [ ] 作業中のClaude Code、Codex、CLI処理を終了または保存した
- [ ] 現在インストール中の`CLI Commentator.app`のバージョンを記録した
- [ ] 元のアプリへ戻せるバックアップまたは再入手手段がある
- [ ] テスト対象がこのリポジトリから作られた内部成果物だと確認した
- [ ] 実データを変更する操作では、内容を読まずに承認しない
- [ ] 表示が崩れた場合は、Managed Terminalから承認や長文入力を行わない

## 4. v0.2.2 Unsigned候補の導入

Codexが導入を担当する場合、HUMANは次の3点だけ確認します。

1. テスト対象のバージョンとcommitが明示されている
2. 現在の公式アプリが復元可能な場所へ退避されている
3. テスト終了後に公式アプリを元へ戻すか、テスト版を継続利用するか選べる

HUMANが`.dmg`から導入する場合:

1. Macの種類に合う成果物を選ぶ
   - Apple Silicon: `aarch64`
   - Intel: `x64`
2. `.dmg`を開く
3. `CLI Commentator.app`を`Applications`へドラッグする
4. Finderの`アプリケーション`から起動する

Unsigned版がmacOSに止められた場合:

1. Finderで`CLI Commentator.app`を右クリックする
2. `開く`を選ぶ
3. 警告内容を確認して`開く`を選ぶ
4. まだ止められる場合は、`システム設定` → `プライバシーとセキュリティ` → CLI Commentatorの`このまま開く`を選ぶ

`壊れているため開けません`と表示された場合は、自己判断で別サイトの回避手順を使わず、Codexへ連絡してください。quarantine解除は、このリポジトリから取得した内部成果物だと確認できた場合だけ、最後の手段として行います。

## 5. 初期設定と基本操作

### 5.1 Desktop Server

アプリ右側の`Desktop Server`パネルを確認します。

- `STATE`: `稼働中`
- `HEALTH`: `OK`
- `Version`: テスト対象のバージョン
- `Platform`: Macの種類と一致

停止中なら`Start`を押します。`HEALTH: OK`と画面上部の`接続中`が出るまで待ちます。

`Stop`はサーバーを止めます。Claude Codeなどが動いている最中に押すとセッションも終了する可能性があるため、保存や作業完了を確認してから使います。

### 5.2 起動するCLI

`実況を始める`で次の順に設定します。

1. `Claude Code（推奨）`、`Codex`、`bash`、`Custom`から選ぶ
2. `作業フォルダ`へ対象プロジェクトの絶対パスを入力する
3. `Claude Codeを起動`などの起動ボタンを押す

通常のHUMANテストでは`Claude Code（推奨）`を使います。`詳細設定`のコマンドと引数は、Custom動作を確認するとき以外は変更しません。

### 5.3 Managed Terminal

- 白または黒の端末領域をクリックすると直接入力できます
- `Ctrl+C`は実行中の処理を中断します
- `クリア`は表示を消します。処理そのものを停止するボタンではありません
- 現在のセッション名が`Managed Terminal`の上に表示されます

### 5.4 実況と解説

- `口調`: `標準` / `関西弁` / `ずんだもん風（テキスト）`
- `表示`: `実況＋解説` / `実況のみ` / `解説のみ`
- `Ruleset`: Claude Code、Codex、汎用のどの判定が使われているかを表示

テスト開始時は、比較しやすいように`標準`と`実況＋解説`を推奨します。その後、好みの組み合わせも試します。

### 5.5 読み上げ（TTS）

1. `読み上げ（TTS）`をオンにする
2. `設定`を開く
3. プリセット、音声、速度、音程、音量を選ぶ
4. `テスト読み上げ`で確認する

`原文も読む`をオンにすると読み上げ量が増えます。普段使いでは最初はオフを推奨します。必要なら`評価ログをJSON出力`で読み上げ動作を記録できます。

### 5.6 スキン

画面上部の`スキン`で`Standard`と`CLI`を切り替えます。見た目だけでなく、文字の読みやすさ、情報の探しやすさ、長時間使用時の疲れを比較します。

### 5.7 プロファイル（任意）

繰り返し使う設定は`＋ 新規`から保存できます。

- 名前
- 入力モード: `PTY（コマンド起動）` / `File（ログ監視）`
- コマンド、引数、作業ディレクトリ
- 口調、ルールセット
- 実況・解説のLLMプロバイダー

APIキーは画面へ入力せず、環境変数で設定します。最初のユーザーテストではプロファイルなしでも構いません。

## 6. 推奨テスト順序

一度に全部を実施する必要はありません。まず`必須`、次に普段の作業、最後に好みの設定を試します。

結果は次の4段階で記録します。

- `OK`: 今回は問題を感じなかった
- `気になる`: 作業は続けられるが改善したい
- `不合格`: 誤操作、作業停止、強い不快感につながる
- `未実施`: 今回は確認していない

`OK`は公開許可を意味しません。

## 7. 必須ユーザーテスト

### UT-01 起動と接続

1. アプリを起動する
2. `Desktop Server`と画面上部の状態を見る
3. 必要なら`Start`を押す

確認:

- [ ] 30秒以内を目安に操作できる状態になる
- [ ] `STATE: 稼働中`、`HEALTH: OK`、`接続中`が矛盾しない
- [ ] 初見でも次に押す場所が分かる
- [ ] エラー時の説明が、専門知識なしで理解できる

### UT-02 Claude Code起動

1. `Claude Code（推奨）`を選ぶ
2. 安全なテスト用リポジトリを`作業フォルダ`へ指定する
3. `Claude Codeを起動`を押す

確認:

- [ ] 指定したフォルダでClaude Codeが起動する
- [ ] 入力欄とカーソルが見える
- [ ] 文字、ロゴ、罫線が重ならない
- [ ] 起動待ちなのか入力可能なのか判断できる

### UT-03 長文入力と折り返し

次のテスト用プロンプトを使えます。

```text
表示テストです。ファイルは変更せず、ツールも使わず、日本語で5項目の箇条書きを返してください。各項目は端末幅近くまで続く2〜3行の長さにしてください。
```

確認:

- [ ] 日本語入力が途中で欠けたり、最後の1文字だけになったりしない
- [ ] 長文が端末幅で自然に折り返される
- [ ] カーソル位置と入力位置が一致する
- [ ] 古い文字や罫線が新しい行へ残らない
- [ ] 出力中でも画面がちらつきすぎない

### UT-04 ウィンドウサイズ変更

Claude Codeの長文が表示された状態で実施します。

1. ウィンドウを狭くする
2. 広くする
3. フルスクリーンへ切り替える
4. 元へ戻す
5. 可能なら外部ディスプレイとの間を移動する

確認:

- [ ] 既存行が新しい幅に合わせて再描画される
- [ ] 罫線、カーソル、入力欄がずれない
- [ ] 文字の重なり、残像、欠落がない
- [ ] サイズ変更後も入力とスクロールを続けられる

表示が崩れた場合は、この時点で`不合格`です。Managed Terminalから承認や長文入力を続けず、スクリーンショットと`Copy Debug bundle`を保存します。

### UT-05 スクロール、クリア、中断

1. 複数画面分の出力を表示する
2. 上下へスクロールする
3. 最下部へ戻る
4. 安全な長めの応答中に`Ctrl+C`を押す
5. `クリア`を押す

確認:

- [ ] 読みたい位置に戻れる
- [ ] 新しい出力で勝手に不自然な位置へ飛ばない
- [ ] `Ctrl+C`で中断でき、結果が理解できる
- [ ] `クリア`後も次の入力ができる
- [ ] クリアと停止の違いが分かる

### UT-06 Stop / Startと再接続

保存が不要なテストセッションで実施します。

1. `Stop`を押す
2. 切断表示を確認する
3. `Start`を押す
4. 再接続後にClaude Codeまたはbashを起動する
5. 再度ウィンドウサイズを変える

確認:

- [ ] 状態表示が停止・起動・接続と一致する
- [ ] 再接続後も端末サイズが正しく反映される
- [ ] 古いセッションの文字が新しい画面へ混ざらない
- [ ] 次に何をすればよいか画面から分かる

### UT-07 PTYサイズの診断（表示崩れ再発時は必須）

1. `bash`を選んで起動する
2. Managed Terminalへ`stty size`と入力する
3. 表示された`行数 列数`を記録する
4. ウィンドウを大きく変える
5. もう一度`stty size`を実行する

確認:

- [ ] ウィンドウ変更後に数値が変わる
- [ ] 広げた場合は通常、列数が増える
- [ ] 数値が変わらない場合はスクリーンショットを残す

### UT-08 承認画面の安全性

通常作業の中で承認画面が現れたときに確認します。危険な操作をわざと発生させる必要はありません。

- [ ] 対象コマンドまたは操作内容を最後まで読める
- [ ] 選択肢、カーソル、現在選択中の項目が分かる
- [ ] 折り返しで重要部分が隠れない
- [ ] 不安なときに拒否・キャンセルできる
- [ ] 画面表示だけを根拠に誤承認しそうな不安がない

少しでも判読しにくい場合は`不合格`です。

## 8. 使用感テスト

### UT-09 実況と解説

標準的な作業を5〜10分行い、各表示モードを試します。

- [ ] 実況が実際の進行と大きくずれない
- [ ] 同じ説明が多すぎない
- [ ] 原文と説明の区別がつく
- [ ] 重要なエラーや承認要求を見落としにくい
- [ ] 説明量が多すぎず、作業の邪魔にならない

### UT-10 読み上げ

- [ ] テスト読み上げが聞こえる
- [ ] 通常進行の音声が多すぎない
- [ ] 緊急・要対応の音声が埋もれない
- [ ] 音声が重なったり、古い内容を遅れて読み続けたりしない
- [ ] 速度、音程、音量を好みに合わせられる
- [ ] 10分使って疲れない

### UT-11 スキンと可読性

`Standard`と`CLI`を各5分程度使います。

- [ ] 主要な操作を探しやすい
- [ ] 文字サイズ、明暗、余白が読みやすい
- [ ] Managed Terminalと実況欄を見分けやすい
- [ ] 長時間見ても目が疲れにくい
- [ ] 好みだけでなく作業効率の差を説明できる

### UT-12 プロファイル

必要な場合だけ実施します。

1. テスト用プロファイルを新規作成する
2. 選択してセッションを起動する
3. 編集する
4. 不要になったテスト用プロファイルだけ削除する

確認:

- [ ] 入力モードと必須項目が理解できる
- [ ] 保存した設定で正しいCLIが起動する
- [ ] 編集結果が反映される
- [ ] 削除対象を誤認しにくい

### UT-13 エラーからの復旧

実際にエラーが起きた場合、無理に直す前に画面を読みます。

- [ ] 想定原因が表示される
- [ ] 最初に試す操作が分かる
- [ ] 確認ポイントやコマンドをコピーできる
- [ ] `Copy Debug bundle`で必要情報をまとめられる
- [ ] 復旧後に通常作業へ戻れる

### UT-14 継続利用

実際の小さな作業を15〜30分以上行います。

- [ ] 入力遅延が気にならない
- [ ] スクロールや再描画が重くならない
- [ ] 実況や音声に疲れない
- [ ] アプリの存在が作業を助けている
- [ ] 通常のターミナルへ戻りたくなる強い理由がない
- [ ] 終了・再起動後も設定や操作感が予想どおり

## 9. セッション終了時の質問

数値だけでなく、自分の言葉で答えます。

1. 今日いちばん良かった点は何か
2. 最初に迷った場所はどこか
3. 最も不安だった操作は何か
4. 反応が遅い、うるさい、読みにくいと感じた場所はどこか
5. 通常のターミナルより便利だった点は何か
6. 通常のターミナルへ戻りたくなった場面はあったか
7. 明日もこのビルドを使いたいか。その理由は何か
8. 1つだけ直せるなら何を直すか

体感評価:

```md
- 始めやすさ: 1 2 3 4 5
- 入力の自然さ: 1 2 3 4 5
- 表示の安心感: 1 2 3 4 5
- 実況の有用性: 1 2 3 4 5
- 読み上げの快適さ: 1 2 3 4 5 / 未使用
- 長時間利用の快適さ: 1 2 3 4 5
- また使いたい: 1 2 3 4 5
```

`1`は非常に悪い、`3`は使えるが改善したい、`5`は非常に良いです。点数にかかわらず、理由を1行以上書きます。

## 11. 修正と再テスト

1. `不合格`または重要な`気になる`をIssue/Todoistへ記録する
2. HUMAN向け解説に、実際の影響と希望する改善を書く
3. 修正PRを作り、自動テストを通す
4. 新しいUnsigned候補を作る
5. 問題が出たテスト項目から再確認する
6. 関係する基本操作と15〜30分の継続利用も再確認する

表示崩れ、誤承認の恐れ、入力欠落、クラッシュ、データ損失の恐れがある場合は、該当ビルドのテストを中止します。

## 13. v0.2.2実機smokeのGo/No-Go基準

ここでの`Go`は、v0.2.2実機smokeを通過したという意味です。公開、配布、Release作成の許可ではありません。

Finderから起動したデスクトップアプリで、30分の通常作業セッションを1本実施します。次のすべてを満たした場合だけ`Go`とします。

1. 描画崩れが0件
2. 定型文だけの読み上げが3回以上連続しない
3. Managed Terminalで入力位置と入力中の文字が常に読める
4. 見逃した要対応が0件、誤った要対応が1件以下
5. 手順書を見ながら、起動から実況開始まで10分以内

1項目でも満たさない場合は`No-Go`です。**満たさない項目だけをIssue化し、その他の気づきはv0.2.3バックログへ送ります。**

## 14. 公開判断との分離

このガイドの完了状態は、`テスト継続`、`修正待ち`、`今回の範囲は問題なし`のいずれかです。`公開Go`という結果は置きません。

前節の`Go`はv0.2.2実機smokeの合格だけを示し、公開Goを意味しません。

HUMANが複数回の実使用を経て十分に納得した後、必要であれば別の公開判断手順を開始します。それまではDraft Releaseと内部成果物のまま維持します。
