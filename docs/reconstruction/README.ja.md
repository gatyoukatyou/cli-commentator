# B案：ローカル共通基盤からの段階移行

2026-09-26、HUMANがB案を採用しました。管理タスクは [tasks #140](https://github.com/gatyoukatyou/tasks/issues/140) です。

## 目標

画面を見なくても、CLIで動くAIの作業を理解し、質問し、必要な場面で承認・停止できるようにします。実況役が今起きたことを伝え、解説役が意味と判断事項を補います。画面・音声・MCP（＝AIから機能を呼び出すための接続規約）は同じ状態と操作サービスを使います。

合格の基準は、利用者が「今何をしている」「何が変わった」「自分は何を決める」を説明できることです。声の自然さや会話の楽しさだけでは完成としません。

## 方針

1. 作業記録・状態・操作・承認を管理する共通基盤を新設します。
2. 既存の端末入力、Desktop、実況の抑制・割り込み等は、必要な検証をして順に移します。
3. 構造化された作業情報を優先し、端末表示の解析は互換接続として残します。
4. 実況・解説・音声の基本動作はローカルで成立させます。作業を実行するAIの接続先は別に選択できます。
5. 難しい解説や音声対話をクラウドへ任せる場合、用途と送信範囲を利用者が選べるようにします。

現行版への継ぎ足しだけで進めるA案は構造上の制約が残ります。別アプリとしてすべて作り直すC案は入力・配布・復旧の再検証が大きくなります。B案では、共通基盤を中心に変えながら既存の動作と検証資産を活かします。

## 守る動作

- すべての説明を根拠のある作業記録に結びつけます。作業AIの報告と実行結果の確認を区別します。
- 応答完了、プロセス終了、人の返答待ち、承認待ち、接続不明を別の状態として扱います。
- 二人の台本は同じ記録から作ります。二人の同意を独立した検証と扱いません。
- 承認を対象の操作・内容・現在のセッションに固定します。古い承認や二重入力で別の作業を進めません。
- AIは人の承認を自己申告できません。AIが使える操作の範囲と、人の判断が必要な操作の範囲を分けます。
- 「説明を止める」と「作業を止める」を区別します。実作業は停止を確認するまで停止済みと伝えません。
- 接続が切れたときに成功と推測しません。モデルが応答しなくても停止操作は使えるようにします。
- 初期設定、聞き返し、承認、停止、履歴、復旧をキーボードとスクリーンリーダーで操作できることを目指します。

## 実装の段階

| 段階 | 成果物 | 完了条件 |
|---|---|---|
| 1：体験と共通操作 | 架空の作業を使う独立デモ。共通状態、二人の台本、画面とMCPの操作 | 承認前に止まり、同じインスタンスの状態を両方の入口から確認できる |
| 2：実作業AI一つとの接続 | 構造化された進行・結果・承認を受け取るアダプター | 実際の開始・応答完了・プロセス終了を区別し、操作結果を照合できる |
| 3：ローカルAIと音声 | 小型モデルによる台本生成、二つの声、聞き返し | 日本語品質、メモリ、音声遅延、他AIとの同時動作、通信断を実測する |
| 4：利用者による評価 | 視覚障害のある利用者と非エンジニアが一つの作業を完遂 | 現在地・変更・判断を理解でき、操作不能箇所を解消する |
| 5：既存機能の移行 | 端末・Desktop・設定・履歴の接続と他CLI対応 | 旧版との比較と復旧手順を確認し、対応能力を明示する |

段階1は製品全体の完成ではありません。短い一連の体験を試す基盤を [PR #483](https://github.com/gatyoukatyou/cli-commentator/pull/483) にまとめました。2026-09-28、HUMANが続行を指示し、段階2の接続先を手元のCodexとして作業を再開しました。29日に実接続、自動テスト26件、画面の開始・説明・停止を確認しました。[段階2の作業計画・接続契約・確認結果](codex-bridge.ja.md) を参照してください。段階2は別のDraft [PR #484](https://github.com/gatyoukatyou/cli-commentator/pull/484) にまとめました。正式版への反映はHUMANが判断します。

## 段階1の範囲

独立した実験アプリ `apps/companion-lab` を追加します。現行のserver・web・Desktopには接続せず、実行中の旧版テストアプリも変更しません。

「調査→修正→テスト失敗→再修正→テスト成功→共有の承認待ち→承認または拒否→終了」を架空のイベントで表します。実際のコマンド実行、ファイル変更、共有、AI推論は行いません。状態と説明の対応を確かめるための決定的な台本です。

初回はプロセス内メモリで管理します。保存・再起動復元を保証しません。根拠と承認を結ぶ契約を確かめた後で永続化を設計します。音声はブラウザの読み上げ機能を暫定使用し、ローカル専用の音声エンジンや異なる二つの声の搭載を保証しません。

画面を使わずにMCPから操作する検証と、画面を開いて字幕と音声を確かめる検証を同じ基盤で行います。MCPモードの画面は同じプロセスが提供するものを使用します。別に起動したデモは別の状態です。

## 次段階の判断材料

手元の評価端末はM4・メモリ24GiBです。ローカルモデルの速度と日本語品質は未測定です。まず小型モデル一つで二人分の台本を作る構成から比較します。モデル名やクラウドの無料枠を基盤に固定しません。

Codex app-server、Claude Codeのフック、ACP等は実作業接続の候補です。各接続先に「観測できる状態」「停止」「承認」「再開」の能力を申告させます。任意CLIで同じ機能が必ず使えるとは扱いません。

参考：[Codex app-server](https://developers.openai.com/codex/app-server)、[Claude Code hooks](https://code.claude.com/docs/en/hooks)、[ACP](https://agentclientprotocol.com/protocol/v1/tool-calls)、[MCP](https://modelcontextprotocol.io/)。採用時に公式情報と実際のインストール版を再確認します。
