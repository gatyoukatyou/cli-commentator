# 段階2：Codexとの実接続

管理タスクは [tasks #140](https://github.com/gatyoukatyou/tasks/issues/140) です。B案の段階1 [PR #483](https://github.com/gatyoukatyou/cli-commentator/pull/483) を土台に、専用のCodexプロセスから実際の進行を受け取ります。既存の端末・Desktopの変更は別の段階です。

## 作業計画と範囲

1. 段階1の状態・根拠・二人の台本を、実接続でも使える共通契約にします。
2. Codexの構造化された通知を受け取り、開始・コマンド実行・返答完了・承認待ち・停止を区別します。
3. 同じ状態を画面とMCPから確認・操作します。AI自身が人の承認を与える機能は設けません。
4. 模擬接続による再現可能な自動テストと、インストール済みCodexによる実接続を照合します。
5. 下書きPRにまとめ、正式版への反映はHUMANの判断を待ちます。

実装はGPT-Luna xhighへ委任し、Ginoが設計・独立レビュー・文書・現物確認を担当します。

最初の作業は、一時的な専用領域にアプリが作る短い日本語の練習用ファイルを読み、内容を説明する一回のタスクです。画面やMCPから任意の命令・作業フォルダ・実行ファイルを指定する機能は対象外です。練習用のCodexは、普段使っているCodexアプリのタスクとは別の子プロセスとして起動します。モデルの文脈には、Codexがもともと読み込む既存の指示ファイルも含まれます。作業対象は練習用ファイルに限定し、既存の指示本文は画面や記録へ公開しません。

実況と解説はこの段階も、確認できた通知をもとにローカルの決定的な台本で作ります。作業AIへの接続はCodexの既存の認証を使います。ChatGPTログインの場合はサブスクの利用枠を使います。ローカルLLMで台本を作ること、二つの声、音声による質問、任意プロジェクトの作業は後続段階です。

## 状態を判断する根拠

| 利用者へ伝えること | 根拠 | 推測しないこと |
|---|---|---|
| 接続の準備ができた | `initialize`の応答と`initialized` | ログイン済み・モデル利用可能とは同一視しません |
| 作業AIが取りかかった | 対象thread/turnの開始通知・応答 | 起動要求を送っただけで開始済みにしません |
| コマンドを実行している | `item/started`の`commandExecution` | モデルの文章だけで実行したと扱いません |
| コマンドが終わった | `item/completed`の実行状態・終了コード | モデルの成功報告と実行結果を混同しません |
| 人の承認を待っている | 対象を照合したサーバーからの承認要求 | AI自身の「承認済み」を採用しません |
| 承認・拒否を送った | 対象要求への単発の応答送信 | 送信だけで作業完了にしません |
| 返答が終わった | `turn/completed`の`completed` | Codexプロセスの終了・成果の正しさとは同一視しません |
| 停止を依頼した | `turn/interrupt`の要求・応答 | 要求を受け付けただけで停止済みにしません |
| ターン停止を確認した | `turn/completed`の`interrupted` | 背景で残るすべてのプロセスの終了を保証しません |
| 専用のCodexプロセスが終了した | 所有する子プロセスの終了観測 | 接続が切れただけで作業成功にしません |
| 状態を確認できない | 異常な通知・接続断・期限超過 | 成功・停止を補って説明しません |

開始・停止・承認には対象セッションと操作を照合します。旧セッション・別ターンの通知や、古い承認画面からの再送で新しい作業を進めません。生の思考過程を解説として公開しません。

## 承認と接続の制限

Codex側には読み取り専用のsandbox（＝コマンドに許すアクセスの制限）と人による承認先を明示します。sandbox外の操作の要求が来た場合、表示した対象についてだけ単発の判断を受け付けます。今後の作業すべてを許す選択や、承認ルールを書き換える選択は設けません。

承認待ちでは操作内容、対象コマンド・作業場所、理由を示します。承認は、この試作が作った一時ファイルを読む既知の単一コマンドと一致する場合に限ります。通信許可や許可ルールの追加を伴う要求は承認できません。未対応の要求は対応済みと装わず、拒否・取消または未対応エラーを返します。

HTTP（＝ブラウザとの通信）の決定経路は、同じ画面からの操作を照合する段階1の保護を引き継ぎます。この仕組みは、同じPC上の別プロセスが人になりすますことまで防ぐ本人認証ではありません。MCPには人の承認を与える道具を登録しません。

Codexの子プロセスには一時的な設定を渡し、既存のMCP・アプリ連携・プラグイン・フック・追加エージェントを無効化します。有効な設定を照合してから練習タスクを開始します。ユーザーの設定ファイル・認証を変更しません。認証情報、生の設定内容、子プロセスの診断出力を画面やGitHubへ公開しません。

## 検証の合格条件

- 架空モードの既存テストが通り、実モードの結果が架空モードとして表示されません。
- 実接続と同じ形式の模擬プロセスで、開始・終了・失敗・承認・割り込み・切断・期限超過を再現できます。
- 古い通知、二重の承認、並行する要求、未知の要求、壊れた通知を取り違えません。
- 画面と公式MCPクライアントが同じ実モードの状態を参照し、MCPから承認を通過できません。
- アプリ終了時に所有する接続・待機処理を解放します。起動中の別のCodexへ停止を送りません。
- 手元のCodexで接続し、実際のコマンド結果とターン完了を観測します。自動テストの模擬結果と区別して記録します。
- キーボードだけで開始・説明・停止を操作でき、接続が切れたときの案内を確認します。実際の音声品質とVoiceOverの使い勝手はHUMAN評価として分けます。

## 起動とMCP操作

この変更を含む作業コピーでNode.js 24と固定した依存関係を使用します。Codexは事前に使える状態である必要があります。アプリはログインや設定変更を代行しません。

```sh
pnpm install --frozen-lockfile
COMPANION_LAB_SOURCE=codex COMPANION_LAB_PORT=43211 pnpm dev:companion-lab
```

表示されたローカルURLを開いて「開始」を選ぶと練習タスクを依頼します。起動するだけでは作業AIを呼びません。「詳しく説明」で根拠を確認し、「もう一度読む」で現在の実況と解説を聞きます。音声停止と作業停止は別の操作です。

AIからMCPで呼ぶ場合は、次を接続先のコマンドとして使います。

```sh
COMPANION_LAB_SOURCE=codex COMPANION_LAB_PORT=43211 pnpm --silent mcp:companion-lab
```

このMCPプロセスが案内する人の操作画面と、MCPの操作結果が同じ状態を共有します。別に起動した画面は別の状態です。同じポートで両方を起動しません。

| MCPツール | 操作 |
|---|---|
| `start_codex_companion_lab` | 最新の世代番号を指定して固定タスクを開始 |
| `get_codex_companion_lab_state` | 現在の状態と世代番号を取得 |
| `explain_codex_companion_lab` | 現在の説明と根拠を取得 |
| `summarize_codex_companion_lab` | 観測した進行の要約を取得 |
| `stop_codex_companion_lab` | 所有する作業と接続の停止を要求 |

実モードには架空作業の「次へ」「保留」のツールがありません。承認は人の操作画面から対象を確認して返します。

接続の実行ファイル・モデル・推論強度は、起動する側の環境変数`COMPANION_LAB_CODEX_BIN`、`COMPANION_LAB_CODEX_MODEL`、`COMPANION_LAB_CODEX_REASONING_EFFORT`で指定できます。画面やMCPの引数には追加しません。検証は手元のCodexと`gpt-6-luna` / `low`で行います。

`COMPANION_LAB_SOURCE`を省くと従来の架空モードです。未対応の値を指定した場合は起動を止め、架空モードへ黙って切り替えません。

## 接続設計の事前確認

2026-09-28、Ginoはアプリの実装とは別の一時プローブで、手元の `codex-cli 0.157.0` に接続しました。認証方法は既存のChatGPTログイン、検証の指定モデルは`gpt-6-luna`、推論強度は`low`です。モデル候補一覧でも、このモデルの提供を確認しました。実装担当の指定は別に`gpt-6-luna` / `xhigh`です。

- 有効設定で全4件の既存MCPが無効であること、hooks・apps・plugins・multi_agentが無効であること、notifyが空でweb_searchが無効であることを照合しました。
- thread/startの返却値は`readOnly` / `networkAccess:false`、承認先は`user`、承認方針は`on-request`でした。
- 通常の検証では、練習用ファイルを読むコマンドの完了・終了コード0、最終返答、ターン完了`completed`を観測しました。その後に入力を閉じ、子プロセスの正常終了を別に観測しました。
- 中断の検証では、turn/interruptの応答後にターン完了`interrupted`を観測しました。その後に入力を閉じ、子プロセスの正常終了を別に観測しました。
- この二つの実接続では承認要求は発生しませんでした。承認の動作確認とは扱いません。

CLIの設定上書きでは、`mcp_servers={}`だけでは既存MCPの無効化を確認できませんでした。各IDの`enabled=false`を渡して、有効設定を再確認する必要があります。この版の`-c`のキーでIDを二重引用符で囲むと、引用符を名前の一部として扱い、起動に失敗しました。名前を安全に表現できない場合は、接続設定を推測して作業を開始しません。

これは接続仕様の事前検証です。次のアプリ経由の結果とは区別します。

## アプリ経由の実接続確認

2026-09-28に確認し、29日に最終版を再検証しました。Ginoは公開のMCP起動コマンドと公式MCPクライアントを使い、実装したアプリ経由で `codex-cli 0.157.0` の作業を確認しました。指定モデルは`gpt-6-luna`、推論強度は`low`です。

- MCPで実モードの5ツールを取得し、練習タスクを開始できました。MCPと同一プロセスの画面が、同じセッションを参照しました。

- 画面用のHTTP経路から停止を要求し、子プロセスの`close`を確認しました。ターン完了の結果は保持しました。
